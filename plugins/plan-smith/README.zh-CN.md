长会话写不出好计划，原因是结构性的：最了解你意图的智能体，恰恰也是上下文被污染得最严重的那个——几十次工具输出、反复的文件转储、走进死胡同的尝试。在那里写计划，就得穿过噪声去写；换到一个全新的子智能体里写，意图又丢了。

**plan-smith 通过拆分工作来拒绝这种取舍。** 主智能体把它唯一独有的资产——会话上下文——全部用于*意图提炼*，产出一份结构化的上下文包。随后，一个上下文干净的 `plan-writer` 智能体依据这份上下文包锻造计划，指导它的是一套久经实战检验的推理框架库，以及两种经过验证的写作风格之一。完成的计划会被**原样**转交——绝不做摘要。

## 它能做什么

- **只提炼意图，主智能体不执笔**——技能从整段对话中抽取目标、硬约束、**被否决的备选方案**、已定的决策和相关文件，整理成一份上下文包。抽取对上下文噪声的鲁棒性远高于写作。
- **一次确认关卡**——动笔之前，先把上下文包展示给你：*“这是我提炼出的意图和约束——对吗？”* 每个推断出的字段都会标记为 `⚠guess` 并逐一确认。一条能纠正意图的流水线，永远胜过一份针对错误意图写得干干净净的草稿。
- **干净上下文锻造**——`plan-writer` 在没有会话噪声的环境中运行：只有上下文包 + 框架规范 + 风格指令。它对你的代码库只读；只写入指定的输出文件——计划本身，relay 第 2 轮时还有 audit.md——并且只返回路径，不返回正文。
- **物有所值的推理框架库**——26 个框架（逆向推导、事前验尸、粗略估算、约束优先、激励核算……），提炼自一项 26 份计划的实证实验，经过 100 份计划的验证语料库压力测试，并且**经一次受控 A/B 实验修正：在一个规格完整的构建任务上，使用框架的计划输给了不用框架的基线**——修正方案是 `spec-coverage`，外加下文的 Gate 0 路由规则。每个框架都附带其**必需组件**（缺了它们，框架就沦为装饰），以及用于自动选择的路由谓词。
- **两种经过验证的写作风格 + relay**——`opus` 风格（覆盖优先的严谨初稿，附诚实的自白日志）和 `fable` 风格（审查结构的修订，把判断编码为规则）。**relay 模式**把两者串联起来：初稿 → 自白 → 带 T1–T6 污染审计的对抗式修订——这是原始实验中观察到的最强流水线。
- **Gate 0：知道什么时候框架会帮倒忙** *（1.1 新增）*——在选择任何框架之前，流水线先问：*“如果照字面执行，危险在于选错了，还是漏掉了？”* 规格已经完整、风险在于遗漏的任务属于 **build-out**，会被路由到 `spec-coverage`（需求 × 表面的完整性矩阵），因为收窄型框架会默许遗漏它们没有选中的一切。这条规则之所以存在，是因为一份用了框架的计划输给了没用框架的计划——见 FAQ。
- **不仅规定零件，还规定接线** *（1.2 新增）*——build-out 计划必须包含一条 **load-bearing path（承重路径）**：一旦失败就会让产物失去意义的那唯一一条路径，写成不超过 5 跳的链条，每一跳都要写明它的守卫条件，*以及该守卫条件首次成立的位置*，另附一张没有空单元格的冷启动表。每条 `build` 需求还必须在**表格之外写一句动词句**（*当 ⟨参与者⟩ 执行 ⟨动作⟩ 时，会发生 ⟨结果⟩；缺失时表现为 ⟨症状⟩*）。这一条款的来由是：一份计划在表面覆盖率上拿了满分，交付的产物却连主要交互都毫无反应——零件一个不少，串起它们的链条却从没被写下来。
- **在你看到计划之前先做接线审计** *（1.2 新增）*——对于 build-out，会由**第二个全新的** plan-writer 实例，用五个文档层面的问题审计完成的计划（未填写的跳、冷启动表中的空单元格、指向计划从未创建的符号的跳、缺少动词句的台账行、只在正文中声称而没有在 “done” 中以命令给出的保证）。作者无法审计自己的遗漏。写作阶段的 token 会多花约 20–35%，换来的是靠阅读看不出的那一类缺陷。
- **按实现者的能力为机制做预算** *（1.3 新增）*——Gate 0 现在还会记录**由谁来实现这份计划**，因为计划要求的每一个部件（一条构建链、一个锁定版本的依赖、一个引用另一个配置的配置）对弱实现者来说都是又一个可能复现失败的环节。在一项 9 单元的迁移测试中，把强模型的计划交给最弱的模型，六个单元中有五个*在构建步骤就*挂掉了，比用它自己那份朴素的计划时挂得更早。因此，弱实现者或未知实现者会拿到要求机制最少的计划——没有构建链，依赖写成完整可复制的字符串，也不设它无法运行的命令形式完成标准。
- **可复制的胶水代码——发布前已验证** *（1.4 新增）*——面向弱实现者或未知实现者，计划现在会把风险最高的衔接代码写成**可逐字复制的代码块**：依赖别名那一行、带精确签名的符号表，以及初始状态声明。能复制的东西就不会被幻觉出来——仅仅把 CDN URL 变成可复制的，幻影版本就已从 5 起降到 0，剩下的失败全是凭记忆而非复制写出的胶水代码。与以往版本不同，这一条款在*发布之前*就通过了预先登记的验证关卡：与知情基线相比（各 n=4），胶水导致的失败 1 比 2，阶梯中位数 L5 对 split——其中包括该测试系列的**首次 stage CLEAR**（关卡通关）。
- **无损交付 + 回顾数据**——计划文件完整呈现，每次的结果（采纳 / 修改 / 否决）都会追加到上下文包中，逐步积累数据，用于持续调优框架路由。

## 安装

### 通过 Claude Code 插件市场

1. 在 Claude Code 中运行 `/plugin`。
2. Marketplaces → Add Marketplace。
3. 输入 URL：`https://github.com/zeriong/because-i-needed.git`（或本仓库的本地路径）。
4. 安装 `plan-smith`。

### 或通过 CLI

```bash
claude plugin marketplace add https://github.com/zeriong/because-i-needed.git   # 或本地路径
claude plugin install plan-smith@because-i-needed
```

### 或直接写入 `~/.claude/settings.json`

```json
{
  "extraKnownMarketplaces": {
    "because-i-needed": {
      "source": { "source": "git", "url": "https://github.com/zeriong/because-i-needed.git" }
    }
  },
  "enabledPlugins": { "plan-smith@because-i-needed": true }
}
```

## 用法

```
/plan-smith:plan-smith 把会话存储从 Redis 迁移到 Postgres
/plan-smith:plan-smith frame=premortem style=relay 付费 Newsletter 的发布计划
/plan-smith:plan-smith style=fable 审查并加固部署运维手册
```

也可以直接用自然语言提出——*“帮我写一份 X 的计划”* 就会触发该技能。参数：

| 参数 | 取值 | 默认值 |
|---|---|---|
| `frame` | [frames.md](skills/plan-smith/references/frames.md) 中的任意框架 | 由 4 个谓词自动路由，并记录理由 |
| `style` | `opus` \| `fable` \| `relay` \| `auto` | `auto`——根据任务信号路由，并记录理由 |

产物保存在 `plans/<slug>/` 中：`packet.md`、`plan.md`（relay 模式下另有 `draft.md`、`audit.md`）。

## 流水线

```
阶段 1 — 意图提炼 (主智能体)
  对话 ──▶ 上下文包 ──▶ 用户确认关卡 (解决 «⚠guess» 字段)

阶段 2 — 隔离写作 (plan-writer 智能体, 全新上下文)
  上下文包 + 框架规范 + 风格指令 ──▶ plans/<slug>/plan.md
  relay: opus 风格初稿 (+ 自白) ──▶ fable 风格修订 (+ T1–T6 审计)

阶段 2c — 接线审计 (全新 plan-writer 实例; 仅限 build-out)
  plan.md ──▶ 5 个文档层面的问题 ──▶ wiring-audit.md ──▶ 最小补充

阶段 3 — 无损转交 (主智能体)
  原样呈现计划文件 ──▶ 用户裁定 ──▶ 在上下文包末尾追加一行回顾
```

为什么拆分有效：*想要正确的计划*需要会话上下文（阶段 1 的资源）；*不受污染的写作*需要隔离（阶段 2 的资源）；*不失真的交付*需要文件契约（阶段 3 的规则）。单个智能体无法同时具备这三者——流水线可以。

## 框架与风格

- **[frames.md](skills/plan-smith/references/frames.md)**——6 个家族（逆向、否定/失败、定量/约束、诊断、多视角、形式）共 26 个框架，每个都包含起点、必需组件、失败模式，以及从语料库中总结出的注意事项。路由**先过 Gate 0**——*是决策文档还是 build-out？*（规格完整、风险在于遗漏的任务交给 `spec-coverage`，因为收窄型框架会默许遗漏）——然后是四个谓词：*不确定性在哪里 / 资源有多刚性 / 执行者有多少认知余量 / 能否就度量标尺达成一致*。
- **[styles.md](skills/plan-smith/references/styles.md)**——两种写作规范与 relay 协议。风格是提示词层面的规范，**不是**模型选择——设计上可在任何模型上运行（跨模型可移植性仍在通过回顾数据验证中）。

## 实测结果

以下每一条结论都来自实验室实测，而非估算（数据：z-lab `plan-smith-lab/`，系列 `tco/`、`transfer/`）。

**得到*可用*产物的总成本**（含修复循环；弱实现者，固定的修复提示词模板，每组 n=4 条链）：

| 阶段 | baseline plan | plan-smith v1.4 |
|---|---|---|
| 计划（opus） | 229k | 689k——**贵 3.0 倍**（读取四份技能文档） |
| 实现 ×4（haiku） | 6,968k | 4,069k——**便宜 42%** |
| 修复至 DONE | **8,380k**（4 轮） | **620k**（1 轮）——**便宜 13.5 倍** |
| **合计：4 个可用产物** | **15.58M** | **5.38M——便宜 65.5%** |

取整来看：基线 100 + 修复 116 = 216；plan-smith 66，直接完成。不只是数字，还有机制：两边的修复提示词是完全相同的模板，所以差距来自**每份计划所产生的缺陷类型**——plan-smith 唯一的失败是其可复制代码块漏掉的一个符号（一行修复；那条链最终达成了该测试系列的首次 stage CLEAR），而基线的失败是跨组件的契约不匹配（一次接口重建，一次历时三轮的打地鼠式修补）。

**有据可查的附带效果：** URL 改为可复制字符串后，幻影依赖版本 5 → 0；4/4 个重复实验复现了完全相同的 CDN 行和文件布局；整个测试系列中仅有的几次 stage CLEAR 全部来自 plan-smith 的单元。

**局限，同一口气说清：** 修复样本小（2 条链对 1 条），只有一个任务、一个弱实现者——换成强实现者时差距会缩小，因为强模型不用这个技能也能成功。基线修复开销的一半来自单独一条链。

## 设计不变量

1. 主智能体**从不亲自写计划**——它只提炼意图；抽取经得住上下文噪声，写作经不住。
2. **没有确认过的上下文包就不动笔**——每个推断字段都先标记 `⚠guess`，并先与用户确认解决。判断存在歧义时，立即询问。
3. 撰写者的输入是**自包含的**（上下文包 + 内联的框架/风格规范）——不访问会话，不猜测路径。
4. **原样转交**——计划文件完整呈现；做摘要即违反契约。
5. 风格是**提示词规范，而不是模型选择**——提炼自一项 26 份计划的受控实验，并经过 100 份计划验证语料库的压力测试；relay 串联和跨模型可移植性仍属“有前景但未验证”，由回顾数据持续积累证据。

## FAQ

**为什么不让主智能体直接写计划？** 因为它的上下文恰恰被赋予它意图的那段会话污染了。抽取（挑出信号）经得住噪声，写作经不住。plan-smith 只把被污染的上下文用在它仍然擅长的唯一一件事上。

**子智能体不会丢失对话中的细微之处吗？** 这正是上下文包存在的意义——目标、约束、*被否决的备选方案*（免得撰写者再次提出）、已定的决策以及每个文件的要点，全部在动笔之前由你在关卡处确认。

**什么时候值得为 relay 付双倍成本？** 难以回退或 blast radius 很大的决策，以及要执行好几个月的计划。审计记录（`audit.md`）会写明修订改了什么、保留了什么以及原因——最终的合并决定权始终在你手里。

**框架会让计划变得*更糟*吗？** 会——而且确实发生过，这正是 1.1 版诞生的原因。在一次受控 A/B 实验中（同一模型、同一个规格完整的任务：一款有 10 个关卡、一个物理循环和一项明确 UI 需求的浏览器游戏），使用 `backward` 框架的计划比不用框架的基线长 38%，却少了 **41% 的可实现指令**；正文约 37% 的篇幅在讲述自己的方法论；把音效、粒子和移动端当作 “off-anchor” 砍掉；对分数、星级、进度保存*以及技术栈*只字未提；还把用户明确提出的三项需求之一重新归类为 “cosmetic”。基线交付了 `audio.ts`、`effects.ts`、`storage.ts`、`types.ts`；用了框架的那份一个都没交付。随后做了三项修正：锚点列表不再能充当范围过滤器；“这个选择是 canonical 的”可以结束一次推导，但永远不能结束一份规格；**Gate 0** 如今会让 build-out 完全绕开收窄型框架。

**token 成本划算吗？** 这是实测，不是估算——完整表格见[实测结果](#实测结果)。以得到*可用*产物为准、含修复循环计算：plan-smith 的计划**写作成本高 3.0 倍**，随后又成倍赚了回来——实现**便宜 42%**，修复**便宜 13.5 倍**——得到四个可用产物的总成本为 **5.38M 对 15.58M token（便宜 65.5%）**。差距来自缺陷类型：plan-smith 唯一的失败是一个漏掉的符号，一行即可修复；而基线的失败是跨组件的契约不匹配。实验室里同样记录了坦诚的局限：修复样本极小，只有一个任务、一个弱实现者；换成强实现者时差距会缩小（强模型不用这个技能也能成功）。完整数据：z-lab `plan-smith-lab/tco/`。

**这些风格的依据是什么？** 一项受控实验：同样的 26 个规划任务分别在两种不同的模型指纹下执行，然后进行对比审计。审计把每种指纹提炼成一条可复现的写作指令；把两者串联（relay）在那次实验中产出了最强的成果——但这只是单次运行的证据，所以流水线把 relay 视为“有前景”而非“已证实”，并持续积累回顾数据来检验它。
