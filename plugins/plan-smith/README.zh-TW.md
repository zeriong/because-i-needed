冗長的工作階段之所以產出糟糕的計畫，有其結構上的原因：最了解你意圖的代理，同時也是上下文汙染最嚴重的那一個——數十次工具輸出、一再重複傾印的檔案內容、走不通的死路。在那裡寫計畫，等於隔著雜訊寫作；改在全新的子代理中寫，則會失去意圖。

**plan-smith 透過拆分工作，拒絕這種兩難取捨。** 主代理把它唯一獨有的資產——工作階段上下文——全部投入*意圖提煉*，產出結構化的上下文封包。接著由乾淨上下文的 `plan-writer` 代理依據這個封包鍛造計畫，並以久經考驗的推理框架庫，以及兩種經過驗證的寫作風格之一作為指引。完成的計畫會**原封不動地**轉交——絕不摘要。

## 它能做什麼

- **意圖提煉，而非由主代理撰寫**——技能會從整段對話中擷取目標、硬性限制、**已否決的替代方案**、已定案的決策以及相關檔案，整理成封包。面對上下文雜訊，擷取遠比撰寫來得穩健。
- **一道確認閘門**——在開始撰寫之前，先把封包給你看：*「這是我提煉出的意圖與限制——對嗎？」* 每個推測出的欄位都會標記 `⚠guess` 並逐一確認。能修正意圖的管線，永遠勝過針對錯誤意圖寫出的漂亮草稿。
- **乾淨上下文鍛造**——`plan-writer` 在沒有工作階段雜訊的環境中執行：只有封包 + 框架規格 + 風格指示。它對你的程式碼庫唯讀；只寫入指定的輸出檔案——計畫本身，relay 第 2 輪另含 audit.md——並回傳路徑，而非內文。
- **物有所值的推理框架庫**——26 個框架（反向推導、事前驗屍、粗略估算、限制優先、誘因盤點……），提煉自一場涵蓋 26 份計畫的實證實驗，經過 100 份計畫的驗證語料庫壓力測試，並**經由一場對照 A/B 測試修正：在該測試中，套用框架的計畫在一個規格完整的建置任務上輸給了未套用框架的基準**；修正方式是 `spec-coverage`，再加上後述的 Gate 0 路由規則。每個框架都附有**必要組件**（一旦缺少，框架就會淪為裝飾的部分），以及供自動選擇用的路由述詞。
- **兩種經過驗證的寫作風格 + relay**——`opus` 風格（涵蓋優先、紀律嚴謹的草稿，附誠實的自白紀錄）與 `fable` 風格（稽核結構的修訂，把判斷寫成規則）。**Relay 模式**會將兩者串接：草稿 → 自白 → 附帶 T1–T6 汙染稽核的對抗式修訂——這是原始實驗中觀察到最強的管線。
- **Gate 0：知道框架何時會幫倒忙** *（1.1 新增）*——在選擇任何框架之前，管線會先問：*「若照字面執行，風險在於選錯了，還是漏掉了？」* 規格已完整、風險在於遺漏的任務屬於 **build-out**，會被導向 `spec-coverage`（需求 × 表面的完整性矩陣），因為收窄範圍的框架，等於默許遺漏它們沒有選中的一切。這條規則之所以存在，是因為一份套用框架的計畫輸給了未套用框架的計畫——詳見 FAQ。
- **不只規定零件，也規定接線** *（1.2 新增）*——build-out 計畫必須包含一條**承重路徑（load-bearing path）**：也就是一旦失效、產出物就失去意義的那唯一一條路徑，寫成不超過 5 跳（hop）的鏈，每一跳都要寫明它的守衛條件，*以及該條件最初在何處成立*，並附上一張沒有空白欄位的冷啟動表。每一項 `build` 需求也都必須附上一句**表格外的動詞句**（*當⟨行為者⟩執行⟨動作⟩時，會發生⟨結果⟩；若缺少它，會表現為⟨症狀⟩*）。這條規則之所以存在，是因為曾有一份計畫在表面涵蓋率上拿到滿分，交付的產出物卻連主要互動都毫無作用——每個零件都在，但貫穿它們的那條鏈從來沒被寫下來。
- **在你看到計畫之前先做接線稽核** *（1.2 新增）*——對於 build-out，會由**第二個、全新的** plan-writer 實例，依五個文件層級的問題稽核完成的計畫（未填寫的跳、冷啟動表中的空白欄位、指向計畫從未建立之符號的跳、缺少動詞句的帳本列，以及以散文宣稱、而非在「done」中以指令證明的保證）。作者無法稽核自己的遺漏。撰寫階段的 token 用量約增加 20–35%，換來的是閱讀時看不出來的那一類缺陷。
- **依實作者編列機制預算** *（1.3 新增）*——Gate 0 現在也會記錄**由誰來實作這份計畫**，因為計畫要求的每一個零件（建置鏈、鎖定版本的相依套件、引用另一份設定的設定檔），對弱實作者來說都是又一個可能無法重現的環節。在一項 9 格的轉移測試中，把強模型的計畫交給最弱的模型，六格中有五格*死在建置步驟*，比它照自己那份樸素的計畫做時還要早。因此，弱或未知的實作者會拿到要求最少機制的計畫——沒有建置鏈、相依套件寫成可直接複製的完整字串、不含它無法執行的指令式完成條件。
- **可複製的黏合碼——發布前已驗證** *（1.4 新增）*——針對弱或未知的實作者，計畫現在會把風險最高的連接程式碼寫成**可逐字複製的區塊**：相依套件別名那一行、附精確簽章的符號表，以及初始狀態宣告。可以複製的東西就不會被幻覺捏造——光是讓 CDN URL 可以直接複製，幽靈版本就已從五起降為零，而剩下的死亡案例，都是憑記憶重寫、而非直接複製的黏合碼。與先前的版本不同，這項條款在*出貨前*就通過了預先登錄的閘門：對照一個知情的基準（各 n=4），黏合碼死亡 1 對 2，階梯中位數 L5 對分歧——其中包括該測試系列**首次出現的關卡 CLEAR**。
- **無損交付 + 回顧資料**——計畫檔案會完整呈現，每一次的結果（採用／修改／否決）都會附加到封包中，逐步累積用來調校框架路由的資料。

## 安裝

### 透過 Claude Code 外掛市集

1. 在 Claude Code 中執行 `/plugin`。
2. Marketplaces → Add Marketplace。
3. 輸入 URL：`https://github.com/zeriong/because-i-needed.git`（或此儲存庫的本機路徑）。
4. 安裝 `plan-smith`。

### 或透過 CLI

```bash
claude plugin marketplace add https://github.com/zeriong/because-i-needed.git   # 或本機路徑
claude plugin install plan-smith@because-i-needed
```

### 或直接寫入 `~/.claude/settings.json`

```json
{
  "extraKnownMarketplaces": {
    "because-i-needed": {
      "source": { "source": "git", "url": "https://github.com/zeriong/because-i-needed.git" }
    }
  },
  "enabledPlugins": { "plan-smith@because-i-needed": true }
}
```

## 使用方式

```
/plan-smith:plan-smith 將工作階段儲存區從 Redis 遷移到 Postgres
/plan-smith:plan-smith frame=premortem style=relay 付費電子報的上線計畫
/plan-smith:plan-smith style=fable 審查並強化部署維運手冊
```

或直接用自然語言提出——說 *「幫我寫一份 X 的計畫」* 就會觸發這個技能。參數：

| 參數 | 值 | 預設 |
|---|---|---|
| `frame` | [frames.md](skills/plan-smith/references/frames.md) 中的任一框架 | 依 4 個述詞自動路由，並記錄理由 |
| `style` | `opus` \| `fable` \| `relay` \| `auto` | `auto`——依任務訊號路由，並記錄理由 |

產出物會存放在 `plans/<slug>/`：`packet.md`、`plan.md`（relay 模式下另有 `draft.md`、`audit.md`）。

## 管線

```
階段 1 — 意圖提煉（主代理）
  對話 ──▶ 上下文封包 ──▶ 使用者確認閘門（解決 «⚠guess» 欄位）

階段 2 — 隔離撰寫（plan-writer 代理，全新上下文）
  封包 + 框架規格 + 風格指示 ──▶ plans/<slug>/plan.md
  relay：opus 風格草稿（+ 自白）──▶ fable 風格修訂（+ T1–T6 稽核）

階段 2c — 接線稽核（全新 plan-writer 實例；僅限 build-out）
  plan.md ──▶ 5 個文件層級問題 ──▶ wiring-audit.md ──▶ 最小幅度補充

階段 3 — 無損轉交（主代理）
  計畫檔案原文呈現 ──▶ 使用者裁決 ──▶ 回顧紀錄附加至封包
```

拆分之所以有效：*想要對的計畫*需要工作階段上下文（階段 1 的資源）；*不受汙染的撰寫*需要隔離（階段 2 的資源）；*毫無損傷的交付*需要檔案契約（階段 3 的規則）。單一代理無法同時擁有這三者——管線可以。

## 框架與風格

- **[frames.md](skills/plan-smith/references/frames.md)**——6 個家族（反向、負面／失敗、量化／限制、診斷、多視角、形式）共 26 個框架，各自附有起點、必要組件、失敗模式，以及從語料庫歸納出的注意事項。路由會**先執行 Gate 0**——*是決策文件，還是 build-out？*（規格已完整、風險在於遺漏者，會導向 `spec-coverage`，因為收窄範圍的框架會默許遺漏）——接著才是四個述詞：*不確定性在哪裡／資源有多僵固／執行者有多少認知餘裕／能否對某個尺度達成共識*。
- **[styles.md](skills/plan-smith/references/styles.md)**——兩種寫作紀律與 relay 協定。風格是提示詞層級的紀律，**而不是**模型選擇——設計上可在任何模型上運作（跨模型的可移植性仍在透過回顧持續驗證中）。

## 實測結果

以下每一項主張都是實驗室的實測值，而非估計（資料：z-lab `plan-smith-lab/`，系列 `tco/`、`transfer/`）。

**達成*可運作*產出物的總成本**（含修復迴圈；弱實作者、固定的修復提示詞範本，每組 n=4 條鏈）：

| 階段 | 基準計畫 | plan-smith v1.4 |
|---|---|---|
| 計畫（opus） | 229k | 689k——**貴 3.0 倍**（需讀取四份技能文件） |
| 實作 ×4（haiku） | 6,968k | 4,069k——**便宜 42%** |
| 修復至 DONE | **8,380k**（4 輪） | **620k**（1 輪）——**便宜 13.5 倍** |
| **4 個可運作產出物的總計** | **15.58M** | **5.38M——便宜 65.5%** |

以約略數字來看：基準 100 + 修復 116 = 216；plan-smith 66，完成。重點不只是數字，而是機制：兩邊的修復提示詞是完全相同的範本，所以差距來自**每份計畫所產生的缺陷類別**——plan-smith 唯一的一次失敗，是它的可複製區塊漏掉了一個符號（一行就修好；那條鏈最後達成了該測試系列的首次關卡 CLEAR），而基準的失敗則是跨元件的契約不一致（一次介面重建，一次歷時三輪的打地鼠）。

**有憑有據的附帶效果：** URL 改為可複製字串後，幽靈相依版本從 5 降為 0；4/4 次重複都重現了完全相同的 CDN 那一行與檔案配置；整個測試系列中僅有的幾次關卡 CLEAR，全都來自 plan-smith 的測試格。

**同時也要說清楚的限制：** 修復樣本很小（2 條鏈對 1 條）、只有一個任務、只有一個弱實作者——換成強實作者時差距會縮小，因為強實作者不靠這個技能也能成功。基準的修復成本有一半來自單一一條鏈。

## 設計不變條件

1. 主代理**絕不撰寫計畫**——它只負責提煉意圖；擷取挺得過上下文雜訊，撰寫則不然。
2. **沒有確認過的封包就不撰寫**——每個推測欄位都會標上 `⚠guess`，並先與使用者釐清。遇到模稜兩可的決策時，立即提問。
3. 撰寫者的輸入是**自給自足的**（封包 + 內嵌的框架／風格規格）——不存取工作階段，也不猜測路徑。
4. **原文轉交**——計畫檔案完整呈現；摘要即違反契約。
5. 風格是**提示詞紀律，而非模型選擇**——提煉自一場涵蓋 26 份計畫的對照實驗，並在 100 份計畫的驗證語料庫中經過壓力測試；relay 串接與跨模型可移植性目前仍屬「有潛力但未驗證」，回顧紀錄正持續累積證據。

## 變更紀錄

發布歷史，以及每個框架或規則*為什麼*被加入，都記錄在 **[CHANGELOG.md](CHANGELOG.md)**（英文）。在鎖定版本之前值得先知道：外掛是從**以版本為鍵的快取**提供的，因此修改原始碼樹並不會影響已安裝的用戶端——每一項行為變更都會以版本號提升的形式發布，而 1.1.1 正是單純為此而存在的版本。

## FAQ

**為什麼不直接讓主代理寫計畫？** 因為讓它得知意圖的那個工作階段，本身就汙染了它的上下文。擷取（挑出訊號）挺得過雜訊，撰寫則不然。plan-smith 只把受汙染的上下文用在它仍然擅長的唯一一件事上。

**子代理不會遺失對話中的細微差異嗎？** 這正是封包存在的目的——目標、限制、*已否決的替代方案*（避免撰寫者再次提出）、已定案的決策，以及每個檔案的要點，全都會在開始撰寫前由你在閘門處確認。

**什麼時候值得為 relay 付出雙倍成本？** 難以逆轉或 blast radius 很大的決策、要執行好幾個月的計畫。稽核軌跡（`audit.md`）會記錄修訂改了什麼、保留了什麼，以及原因——最終的合併決定權仍在你手上。

**框架會讓計畫變得*更糟*嗎？** 會——而且真的發生過，這正是 1.1 存在的原因。在一場對照 A/B 測試中（同一個模型、同一個規格完整的任務：一款有 10 個關卡、物理迴圈，以及一項具名 UI 需求的瀏覽器遊戲），套用 `backward` 框架的計畫比未套用框架的基準長了 38%，**可實作的指示卻少了 41%**；它花了約 37% 的篇幅敘述自己的方法論，把音效／粒子效果／行動裝置當成「off-anchor」砍掉，對分數、星等、進度保存*以及技術堆疊*隻字未提，還把使用者明確提出的三項需求之一重新標為「cosmetic」。基準交付了 `audio.ts`、`effects.ts`、`storage.ts`、`types.ts`；套用框架的那份一個都沒有交付。隨後做了三項修正：錨點清單不得再充當範圍篩選器；「這個選擇是 canonical」可以結束一段推導，但絕不能結束一份規格；而 **Gate 0** 現在會讓 build-out 完全避開收窄範圍的框架。

**token 成本回得了本嗎？** 這是實測，不是估計——完整表格請見[實測結果](#實測結果)。以達成*可運作*產出物的成本計算（含修復迴圈）：plan-smith 的計畫**撰寫成本高出 3.0 倍**，之後卻加倍賺了回來——實作**便宜 42%**、修復**便宜 13.5 倍**——做出四個可運作產出物的總計為 **5.38M 對 15.58M token（便宜 65.5%）**。差距來自缺陷類別：plan-smith 唯一的失敗只是一個一行就能修好的遺漏符號，而基準的失敗則是跨元件的契約不一致。實驗室中也誠實記錄了限制：修復樣本極小、只有一個任務、只有一個弱實作者；換成強實作者時差距會縮小（強模型不靠這個技能也能成功）。完整資料：z-lab `plan-smith-lab/tco/`。

**這些風格的依據是什麼？** 一場對照實驗：同樣的 26 個規劃任務，分別在兩種不同的模型指紋下執行，再進行比較稽核。稽核將每種指紋提煉成可重現的寫作指示；將兩者串接（relay）在該實驗中產出了最強的成果——但這只是單次執行的證據，因此管線將 relay 視為「有潛力」而非「已證實」，並持續累積回顧紀錄來檢驗它。
