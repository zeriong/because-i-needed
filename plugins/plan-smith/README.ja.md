---

長いセッションが悪いプランを生むのには、構造的な理由があります。あなたの意図を最もよく知っているエージェントは、同時にコンテキストが最も汚染されたエージェントでもあるからです — 何十回ものツール出力、繰り返されたファイルダンプ、行き止まりに終わった試行。そこでプランを書けば、ノイズ越しに書くことになります。新しいサブエージェントで書けば、意図が失われます。

**plan-smith は仕事を分割することで、このトレードオフを拒否します**。メインエージェントは唯一無二の資産であるセッションコンテキストを、すべて*意図の蒸留*に費やし、構造化されたコンテキストパケットを作ります。続いてクリーンなコンテキストの `plan-writer` エージェントが、実戦で鍛えられた推論フレームライブラリと、検証済みの 2 つの執筆スタイルのうちの 1 つに導かれて、パケットからプランを鍛え上げます。完成したプランは**原文のまま**届けられ、要約されることはありません。

## Codex

Codex CLI 0.158.0 以降が必要です。インストール後、新しいセッションを開始してください。Claude は `/plugin:skill`、Codex は `$plugin:skill` を使います。共通のスキルと資料はこのプラグインに同梱されています。自動動作を利用する前に `/hooks` で同梱フックを確認して信頼してください。

```bash
codex plugin marketplace add https://github.com/zeriong/because-i-needed.git
codex plugin add plan-smith@bin
```

`$plan-smith:forge <タスク>` を使います。Codex は同じエージェント指示・フレーム・文体で執筆、各リレーパス、監査、分割を新しいコンテキストで実行します。独自の質問ツールを使い、メインのモデルと推論設定を継承します。Opus/Fable は文体名です。パケット確認、独立執筆、原文の引き渡しを維持します。

### Codex 設定

手順・成果物・レビュー基準を共有します。Codex のレビューモデルは設定できますが、Claude と同一の出力や品質を保証するものではありません。Codex 起動前に環境変数を設定し、省略した値は現在のセッションを継承します。委任された CLI は `CXC_MODE=off` で実行され、メインのモードは変わりません。

| 設定 | 動作 |
|---|---|
| `PLAN_SMITH_CODEX_MODEL` | 執筆者 モデル。既定: 現在のセッションのモデル |
| `PLAN_SMITH_CODEX_EFFORT` | 執筆者 推論強度。既定: 現在のセッションの推論強度 |

## できること

- **メインエージェントは書かず、意図を蒸留する** — スキルが会話全体から目標、ハード制約、**却下された代替案**、決定済みの事項、関連ファイルを抽出し、パケットにまとめます。抽出は、執筆に比べてコンテキストのノイズにはるかに強いのです。
- **確認ゲートは 1 回だけ** — 執筆が始まる前に、パケットがあなたに提示されます: *「私が蒸留した意図と制約はこちらです — 合っていますか？」* 推測で埋めたフィールドにはすべて `⚠guess` が付き、確認を受けます。意図を修正できるパイプラインは、誤った意図で書かれたきれいな草稿に必ず勝ちます。
- **クリーンなコンテキストでの鍛造** — `plan-writer` はセッションのノイズなしに、パケット + フレーム仕様 + スタイル指示だけを持って動きます。コードベースに対しては read-only で、指定された出力ファイル（プラン、relay パス 2 では audit.md も、分割時はインデックスとパート）だけを書き、テキストではなくパスを返します。
- **元が取れる推論フレームライブラリ** — 26 個のフレーム（逆算、プレモーテム、封筒の裏の概算、制約優先、インセンティブ会計など）。26 件のプランによる実証実験から蒸留し、100 件のプランからなる検証コーパスでストレステストを行い、さらに仕様が完全なビルドで**フレームを使ったプランがフレームなしのベースラインに負けた統制 A/B によって修正**されています — その修正が `spec-coverage` と、後述の Gate 0 ルーティングルールです。各フレームには、**必須コンポーネント**（欠けるとフレームがただの飾りになってしまう部分）と、自動選択のためのルーティング述語が付属します。
- **検証済みの 2 つの執筆スタイル + relay** — `opus` スタイル（網羅性を優先する規律ある草稿と、正直な告白ログ）と `fable` スタイル（構造を監査する改訂と、ルールとして符号化された判断）。**relay モード**はこの 2 つを連結します: 草稿 → 告白 → T1–T6 汚染監査を伴う敵対的改訂 — 元の実験で観測された中で最も強力なパイプラインです。
- **Gate 0: フレームが害になる場面を見極める** *（1.1 で追加）* — フレームを選ぶ前に、パイプラインは問います: *「文字どおりに従ったとき、危険なのは選択を誤ることか、それとも何かを抜かすことか？」* 仕様が完全でリスクが欠落にある場合、それは **build-out** であり、`spec-coverage`（要件 × サーフェスの完全性マトリクス）にルーティングされます。絞り込み型のフレームは、自らが選ばなかったものの欠落を容認してしまうからです。このルールは、フレームを使ったプランがフレームなしのプランに負けたことから生まれました — FAQ を参照してください。
- **部品だけでなく配線まで仕様化する** *（1.2 で追加）* — build-out のプランには必ず **load-bearing path** を含めます。これは失敗すると成果物が無意味になってしまう唯一の経路で、5 ホップ以下の連鎖として書かれ、各ホップにはそのガードと*そのガードが最初に真になる地点*を明記し、さらに空欄のないコールドスタート表を添えます。すべての `build` 要件には、**表の外に書く動詞文**も必要です（*⟨アクター⟩が⟨アクション⟩すると⟨結果⟩が起こり、それがなければ⟨症状⟩として現れる*）。この条項は、サーフェスカバレッジで満点を取ったプランが、主要なインタラクションが何も起こさない成果物を生んだことから生まれました — 部品はすべて揃っていたのに、それらを通る連鎖が一度も書き出されていなかったのです。
- **プランを目にする前に配線監査を通す** *（1.2 で追加）* — build-out では、**2 つ目の新しい** plan-writer インスタンスが、完成したプランを 5 つの文書レベルの質問で監査します（埋まっていないホップ、コールドスタート表の空欄、プランが作成しないシンボルを指すホップ、動詞文のない台帳の行、「done」のコマンドではなく散文で主張された保証）。書き手は自分の欠落を監査できません。執筆段階のトークンは約 20–35% 増えますが、読むだけでは見えない種類の欠陥をひとつ捕まえられます。
- **機構の量を実装者に合わせて配分する** *（1.3 で追加）* — Gate 0 は**誰がこのプランを実装するのか**も記録するようになりました。プランが要求する部品（ビルドチェーン、固定された依存関係、別の設定を参照する設定）はどれも、弱い実装者にとっては再現に失敗しうる面がひとつ増えることを意味するからです。9 セルの転移テストでは、強いモデルのプランを渡された最も弱いモデルが、6 セル中 5 セルで*ビルドの段階で*脱落しました。自分自身の控えめなプランを渡されたときよりも早い段階です。そのため、弱い実装者や不明な実装者には、機構を最も少なく要求するプランが渡されます — ビルドチェーンなし、依存関係はコピーできる完全な文字列で、実行できないコマンド形式の完了基準はなし。
- **コピーできる接着コード — リリース前に検証済み** *（1.4 で追加）* — 弱い実装者や不明な実装者向けのプランには、最もリスクの高い接続コード（依存関係のエイリアス行、正確なシグネチャ付きのシンボル表、初期状態の宣言）が**そのままコピーできるブロック**として含まれるようになりました。コピーできるものはハルシネーションされません — CDN URL をコピー可能にしただけで、幻のバージョンはすでに 5 件から 0 件に減っており、残った脱落は、コピーせずに記憶から書き起こした接着コードによるものでした。これまでのリリースと異なり、この条項は出荷*前*に事前登録済みのゲートを通過しています: 情報を与えられたベースラインとの比較（各 n=4）で、接着コードによる脱落は 1 対 2、ラダーの中央値は L5 対 割れ — このテスト系列で**初めてのステージ CLEAR** も含みます。
- **大きなプランはインデックスと順序付きのパートで届く** *（1.6 で追加）* — 完成したプランが 20,000 文字を超えると分割します。`plan.md` はポインターだけのインデックスになり、プラン全体は `parts/<category>_<A0–Z99>.md`（文字 = 段階、数字 = 段階内の順序）に移され、各パートは次のパートへのポインターで終わります。分割はすべてのゲートと配線監査がプラン全体を判定した後に行われ、新しい plan-writer が一字も変えずに移し、チェックスクリプトが抜け・重複・順序の入れ替わりがないことを確かめます。理由はまだ測定していない 2 つの仮説です — 長いプランも順に分けて読めば一部を読み飛ばされにくく、ポインターがあればエージェントがたどりやすい。20,000 文字の基準は、振り返りデータが置き換えるまで根拠のない任意値です。実際のライターでコーパスの 20〜37k 文字のプラン 3 つを分割した結果（z-lab `plan-smith-lab/split-1.6.0/`、n=6）、6/6 が最初の試行で欠落なく、パートは 6〜11 個、10,000 文字の目標を超えたパートはなく、opus で分割 1 回あたり約 $0.8・2.5 分でした。分割が実装者の役に立つかは測定していません。
- **ロスのない受け渡し + 振り返りデータ** — プランは全文がそのまま提示され（分割されたプランはインデックスとすべてのパートを順に）、すべての結果（採用 / 修正 / 却下）がパケットに追記されて、フレームのルーティングを時間をかけて調整するためのデータとして蓄積されます。

## インストール

### Claude Code プラグインマーケットプレイスから

1. Claude Code で `/plugin` を実行します。
2. Marketplaces → Add Marketplace を選びます。
3. URL を入力します: `https://github.com/zeriong/because-i-needed.git`（またはこのリポジトリのローカルパス）。
4. `plan-smith` をインストールします。

### または CLI から

```bash
claude plugin marketplace add https://github.com/zeriong/because-i-needed.git   # またはローカルパス
claude plugin install plan-smith@bin
```

### または `~/.claude/settings.json` に直接記述

```json
{
  "extraKnownMarketplaces": {
    "bin": {
      "source": { "source": "git", "url": "https://github.com/zeriong/because-i-needed.git" }
    }
  },
  "enabledPlugins": { "plan-smith@bin": true }
}
```

## 使い方

```
/plan-smith:forge セッションストアを Redis から Postgres に移行する
/plan-smith:forge frame=premortem style=relay 有料ニュースレターのローンチ計画
/plan-smith:forge style=fable デプロイのランブックを見直して強化する
```

自然な言葉で頼むだけでも構いません — *「X のプランを書いて」* でスキルが起動します。引数は次のとおりです。

| 引数 | 値 | デフォルト |
|---|---|---|
| `frame` | [frames.md](skills/forge/references/frames.md) にある任意のフレーム | 4 つの述語で自動ルーティング、根拠を記録 |
| `style` | `opus` \| `fable` \| `relay` \| `auto` | `auto` — タスクのシグナルでルーティング、根拠を記録 |

成果物は `plans/<slug>/` に保存されます: `packet.md`、`plan.md`（relay モードでは + `draft.md`、`audit.md`）。

## パイプライン

```
ステージ 1 — 意図の蒸留 (メインエージェント)
  会話全体 ──▶ コンテキストパケット ──▶ ユーザー確認ゲート («⚠guess» フィールドを解消)

ステージ 2 — 隔離された執筆 (plan-writer エージェント、新しいコンテキスト)
  パケット + フレーム仕様 + スタイル指示 ──▶ plans/<slug>/plan.md
  relay: opus スタイルの草稿 (+ 告白) ──▶ fable スタイルの改訂 (+ T1–T6 監査)

ステージ 2c — 配線監査 (新しい plan-writer インスタンス、build-out のみ)
  plan.md ──▶ 文書レベルの質問 5 つ ──▶ wiring-audit.md ──▶ 最小限の追記

ステージ 2d — 分割 (新しい plan-writer インスタンス、20,000 文字を超えるときのみ)
  plan.md ──▶ インデックス plan.md + parts/<category>_<A0–Z99>.md ──▶ split-check.py (欠落なし・順序どおりを確認)

ステージ 3 — ロスのないリレー (メインエージェント)
  プランを原文のまま提示 (分割時: インデックス + 全パートを順に) ──▶ ユーザーの verdict ──▶ 振り返りを 1 行パケットに追記
```

分業がうまくいく理由: *正しいプランを求めること*にはセッションコンテキスト（ステージ 1 の資源）が、*汚染のない執筆*には隔離（ステージ 2 の資源）が、*損なわれない受け渡し*にはファイル規約（ステージ 3 のルール）が必要です。1 つのエージェントでは 3 つすべてを持てませんが、パイプラインなら持てます。

## フレームとスタイル

- **[frames.md](skills/forge/references/frames.md)** — 6 系統（逆算、否定 / 失敗、定量 / 制約、診断、多視点、形式）の 26 個のフレーム。それぞれに出発点、必須コンポーネント、失敗モード、コーパスから得た watch-outs が付きます。ルーティングでは**まず Gate 0** を通します — *意思決定文書か、build-out か？*（仕様が完全でリスクが欠落にある場合は `spec-coverage` へ。絞り込み型のフレームは欠落を容認してしまうため）— 続いて 4 つの述語: *不確実性はどこにあるか / 資源はどれだけ硬直的か / 実行者の認知的な余裕はどれだけあるか / 尺度に合意できるか*。
- **[styles.md](skills/forge/references/styles.md)** — 2 つの執筆規律と relay プロトコル。スタイルはプロンプトレベルの規律であり、モデルの選択では**ありません** — どのモデルでも動くように設計されています（モデル間の移植性は、振り返りを通じてまだ検証中です）。

## 実測結果

以下の主張はすべて推定ではなく、ラボでの実測値です（データ: z-lab `plan-smith-lab/`、シリーズ `tco/`、`transfer/`）。

***動作する*成果物までの総コスト**（修正ループ込み、弱い実装者、固定の修正プロンプトテンプレート、各群 n=4 チェーン）:

| ステージ | ベースラインのプラン | plan-smith v1.4 |
|---|---|---|
| プラン（opus） | 229k | 689k — **3.0 倍のコスト**（スキル文書 4 つを読み込む） |
| 実装 ×4（haiku） | 6,968k | 4,069k — **42% 削減** |
| DONE までの修正 | **8,380k**（4 ラウンド） | **620k**（1 ラウンド） — **13.5 分の 1** |
| **動作する成果物 4 つの合計** | **15.58M** | **5.38M — 65.5% 削減** |

概数で言えば、ベースラインは 100 + 修正 116 = 216、plan-smith は 66 で完了です。数字だけでなくメカニズムも見てください: 修正プロンプトは両者で同一のテンプレートだったので、差は**各プランが生み出す欠陥の種類**から生じています — plan-smith の唯一の失敗は、コピー可能なブロックが取りこぼしたシンボル 1 つでした（1 行で修正。そのチェーンはテスト系列で初めてのステージ CLEAR で終わりました）。一方、ベースラインの失敗はコンポーネント間の契約の不一致でした（インターフェースの作り直しが 1 件、3 ラウンドに及ぶもぐら叩きが 1 件）。

**裏付けのある副次効果:** URL をコピー可能な文字列にしてから、幻の依存関係バージョンは 5 → 0。4/4 のレプリカが同一の CDN 行とファイル構成を再現。テスト系列全体でステージ CLEAR が出たのは、plan-smith のセルだけでした。

**同じ段落で述べておく限界:** 修正のサンプルは小さく（2 チェーン対 1 チェーン）、タスクは 1 種類、弱い実装者も 1 種類のみです — 強い実装者はスキルなしでも成功するため、差は縮まります。ベースラインの修正コストの半分は、1 本のチェーンに由来します。

## 設計上の不変条件

1. メインエージェントは**プランを決して書きません** — 意図を蒸留するだけです。抽出はコンテキストのノイズに耐えますが、執筆は耐えられません。
2. **確認済みのパケットなしに執筆はしません** — 推測したフィールドにはすべて `⚠guess` を付け、先にユーザーと解消します。判断があいまいなときは、すぐに尋ねます。
3. ライターへの入力は**自己完結**しています（パケット + インラインのフレーム / スタイル仕様）— セッションへのアクセスも、パスの推測もありません。
4. **原文リレー** — プランは全文を提示します（分割されたプランはインデックスとすべてのパートを順に）。要約は規約違反です。
5. スタイルは**モデルの選択ではなく、プロンプトの規律**です — 26 件のプランによる統制実験から蒸留し、100 件のプランからなる検証コーパスでストレステストしました。relay による連結とモデル間の移植性は「有望だが未検証」のままで、振り返りがその証拠を蓄積していきます。

## 変更履歴

リリース履歴と、各フレームやルールが*なぜ*追加されたのかは **[CHANGELOG.md](CHANGELOG.md)**（英語）にあります。バージョンを固定する前に知っておくべきこと: プラグインは**バージョンをキーとするキャッシュ**から配信されるため、ソースツリーを編集してもインストール済みのクライアントには届きません — 動作の変更はすべてバージョンアップとして出荷され、1.1.1 はその理由だけのために存在するリリースです。

## FAQ

**なぜメインエージェントがそのままプランを書かないのですか？** 意図を教えてくれたまさにそのセッションによって、コンテキストが汚染されているからです。抽出（シグナルの拾い出し）はノイズに耐えますが、執筆は耐えられません。plan-smith は、汚染されたコンテキストを、それがまだ得意とする唯一の仕事にだけ使います。

**サブエージェントは会話のニュアンスを失いませんか？** そのためにパケットがあります — 目標、制約、*却下された代替案*（ライターが再提案しないように）、決定済みの事項、ファイルごとの要点まで、すべて執筆が始まる前にゲートであなたが確認します。

**relay は、どんなときに 2 倍のコストに見合いますか？** 元に戻しにくい、あるいは blast radius の大きい決定や、何か月もかけて実行するプランです。監査記録（`audit.md`）には、改訂で何を変え、何を残したか、そしてその理由が記録されます — 最終的なマージの権限はあなたにあります。

**フレームがプランを*悪く*することはありますか？** あります — 実際にそうなったので、1.1 が生まれました。統制 A/B（同じモデル、同じ完全に仕様化されたタスク: 10 ステージ、物理ループ、明示された UI 要件を持つブラウザゲーム）で、`backward` フレームを使ったプランはフレームなしのベースラインより 38% 長かったにもかかわらず、**実装可能な指示は 41% 少なく**、本文の約 37% を自らの方法論の説明に費やし、サウンド / パーティクル / モバイルを「off-anchor」として切り捨て、スコア、星、永続化、*そしてスタック*について沈黙し、ユーザーが明示した 3 つの要件のうち 1 つを「cosmetic」とラベルし直しました。ベースラインは `audio.ts`、`effects.ts`、`storage.ts`、`types.ts` を出荷しましたが、フレームを使った側はそのどれも出荷しませんでした。その後、3 つの修正が行われました: アンカーリストはもはやスコープのフィルターとして働いてはならない、「この選択は canonical である」は導出を終わらせてもよいが仕様を終わらせてはならない、そして **Gate 0** が build-out を絞り込み型のフレームから完全に迂回させる、というものです。

**トークンコストに見合う効果はありますか？** 推定ではなく実測です — 全体の表は[実測結果](#実測結果)を参照してください。修正ループを含めた*動作する*成果物までのコストで見ると、plan-smith のプランは**書くのに 3.0 倍のコスト**がかかりますが、その元を 2 倍以上取り戻します — 実装は **42% 削減**、修正は **13.5 分の 1** — 動作する成果物 4 つまでの合計は **5.38M 対 15.58M トークン（65.5% 削減）** です。差は欠陥の種類から生じます: plan-smith の唯一の失敗は 1 行で直せるシンボルの取りこぼしでしたが、ベースラインの失敗はコンポーネント間の契約の不一致でした。ラボに記録された正直な限界: 修正のサンプルがごく小さく、タスクは 1 種類、弱い実装者も 1 種類のみです。強い実装者では差が縮まります（強いモデルはスキルなしでも成功します）。全データ: z-lab `plan-smith-lab/tco/`。

**スタイルの根拠は何ですか？** 統制実験です: 同じ 26 件のプランニングタスクを 2 つの異なるモデルのフィンガープリントで実行し、比較監査しました。監査によって各フィンガープリントを再現可能な執筆指示へと蒸留し、それらを連結したもの（relay）がその実験で最も強力な成果物を生みました — ただし 1 回の実行による根拠なので、パイプラインは relay を「実証済み」ではなく「有望」として扱い、振り返りを蓄積して検証しています。
